# OG scenarios: design, report, explore

One skill for everything around a scenario run except the solve itself: specifying the reform
before it runs, producing the house deliverable after, and answering whatever else the audience
asks. Two absolutes hold in every mode:

1. **Everything generated is generated by code.** Every number in a table, chart or paragraph is
   computed by a script from the run's actual outputs, never typed from memory or read off another
   chart. Keep the script: each piece of work gets a small directory (script, generated artifacts,
   a two-line README) next to the run it uses, so any figure can be regenerated and audited.
2. **This skill never launches a solve.** Designing, reading, plotting and writing are free. The
   moment a question needs a new run (a redesigned reform, a missing or stale baseline, a
   sensitivity sweep), stop: specify the run, estimate its duration, and ask (og-run, and the
   owner's run rules). Never quietly re-run a solve to fill a gap. Pushing or publishing any product
   also waits for the user.

## Which world

This skill acts on **one** world: the runtime installation reached by `muiogo-ai`,
unless the user explicitly asked for their own live one (`muiogo-live`). Never use
bare `muiogo`, and never fall back to it. Every command prints a `world:` line to
stderr — read it, and name that world when you report a result or a number. Worlds
hold different OG checkouts and different model registries, so the same country
model can exist in both at different commits. Locate the checkout you mean with
`muiogo-ai status` rather than assuming a path. Full rules:
`../WORLD_DISCIPLINE.md`.

## Reading outputs safely

- A run leaves `OUTPUT_BASELINE/` and `OUTPUT_REFORM/`, each with `SS/SS_vars.pkl`,
  `TPI/TPI_vars.pkl` and `model_params.pkl`. They are inputs; never edit them.
- Load with `ogcore.utils.safe_read_pickle` in the country repo's own venv. A pickle is executable:
  only load runs you or the user produced. (The bundled script uses a restricted unpickler that
  accepts numpy objects only.)
- Honesty rules travel with the numbers, stated where the number appears: model levels are not
  currency (`factor` converts; ratios and % changes are quotable); multi-industry consumption is
  `p_tilde·C`, never raw `C`; nominal sector shares are distorted by the numeraire; net exports is a
  residual.
- **Know what the run can answer.** A single-industry run has no industry detail; a reform that
  bundles several changes cannot attribute effects to one of them. Say so instead of producing a
  figure that implies otherwise, and offer the run that would answer it.

## Mode 1: design a scenario

Translate a policy question into a runnable reform spec before anyone runs anything:

- The spec: the exact `updated_params_ref` dict; phase-in paths (year-by-year arrays where phased);
  the fiscal closure (`tG1`/`tG2`, which closure rule) and why; the expected transmission (which
  margins should move, which way); and the estimated runtime.
- **Representability first.** OG-Core has one economy-wide wage and no household sector choice;
  formal/informal wage gaps, sector switching and trade policy are not representable without
  extending the model. Say so up front rather than bending a parameter to fake it. Industry-varying
  `cit_rate`/`tau_c` need a multi-industry model; by-income-group tax parameters do not exist.
- **Fiscal coherence.** A reform that changes revenue must say what absorbs it (closure rule or an
  offsetting instrument), or the transition reports the closure's behaviour, not the policy's
  (og-country-calibration, fiscal consistency).
- **Change one thing per scenario** unless the bundle is the policy; otherwise effects cannot be
  separated later.
- Plot the reform's input paths as part of the spec, so a mis-built phase-in is caught before it
  costs a solve.

## Mode 2: the standard deliverable

Every scenario run ends in the same deliverable; produce it once, completely. Reference:
`OG-PHL/examples/OG-PHL-Example/`.

1. `<Country>_example_output.csv`: `ogcore.output_tables.macro_table(..., var_list=["Y","C","K",
   "L","r","w"], output_type="pct_diff", num_years=10)`.
2. `<name>_plots/`: `ogcore.output_plots.plot_all(base_dir, reform_dir, save_path)`, about 30 PNGs
   (macro and fiscal % changes, r and w, spending, debt and revenue to GDP, by-ability-group bars,
   steady-state lifecycle profiles). These two stock calls are the de facto standard; run them
   first, in the repo's venv. If CSV or plots already exist, check they are newer than the pickles
   before trusting them.
3. `report.md`, from the bundled script (needs only numpy):

   ```bash
   <repo>/.venv/bin/python scripts/scenario_report.py \
     --base <...>/OUTPUT_BASELINE --reform <...>/OUTPUT_REFORM \
     --out report.md [--start-year 2025] [--num-years 10]
   ```

   It writes the macro and fiscal % change tables, steady-state revenue by instrument as % of GDP,
   `D/Y`, and narrative sentences with the numbers filled in and TODO slots for interpretation.
4. A filled `README.md` in the scenario folder: what the reform is (the exact changed parameters and
   their policy meaning), how to re-run, where the deliverables are. Write it while the run context
   is fresh; the fleet's scenario folders are full of unfilled stubs.

Fill every TODO the script leaves (mode 4): the mechanism paragraph, the fiscal-closure caveat, the
distributional paragraph (from the `PctChange_*` by-ability charts), and the units caveat. A table
without the mechanism sentence is not a deliverable. For non-technical prose, quote `r` in
percentage points and say so.

Gaps the stock tooling leaves, filled when relevant:
- **Input diagnostics.** `plot_all` plots outputs only. If the reform perturbs a parameter path
  (phased productivity, `chi_n`, a phased `alpha_G`), plot baseline vs reform for that parameter.
- **Several reforms.** ogcore compares one reform with one baseline. Run the stock pair per reform,
  then build one combined table (rows = variables, one column block per reform, same baseline).

## Mode 3: explore and visualise

Interrogate runs, inputs and outputs beyond the standard set:

- Derive freely: ratios to Y, per-capita and per-cohort cuts, incidence by ability group, growth
  contributions, differences across several runs. Nothing limits you to one baseline and one reform.
- If a result looks wrong, do not explain it away: check the run first (og-solver-diagnosis, and
  the contamination check in og-run-preflight).
- **Pick the best tool for the figure.** The country venvs have matplotlib, pandas and scipy, enough
  for publication-quality statics (use a clean explicit style). For interactivity or heavier data
  handling, make a scratch analysis env (`uv venv`) and feed it data exported from the repo venv as
  CSV or parquet; never install analysis libraries into a model venv or unpickle model objects
  outside it. If a dataviz skill is installed, follow its palette and accessibility rules.
- Charts of inputs (parameter paths, e-matrix slices, `chi_n`) are first-class; they are the
  diagnostic the stock tooling lacks.
- Every figure ships with its script and a caption naming the run directories and units.

## Mode 4: write-ups

Prose shaped to the audience (ministry memo, technical annex, slide narrative, referee response):

- Structure is free. Not free: every quantitative claim traces to a computed value (keep the
  computation in the script; a small "numbers used" table helps); mechanisms are stated as
  mechanisms (which condition, which constraint, which closure); verified facts are separated from
  interpretation.
- State the run provenance once: repo, branch and commit, run directories, calibration file, and
  whether it ran online.
- Drafts are drafts: show the user before anything is sent, published or committed outside the
  analysis directory.

## Checks before shipping

- **Anchor one number to the calibration:** baseline steady-state `D/Y` must equal the repo's
  `debt_ratio_ss`, and baseline revenue/GDP should match the calibration dashboard. If not, you may
  be reading the wrong output directory, or an unconverged run.
- **Confirm the solve completed** (`Time path iteration complete` in the log). Note any guard
  warnings (`K_d has negative elements`) in the caveats. If there is no log, say convergence is
  inferred. If the run looks sick, switch to og-solver-diagnosis before reporting numbers.
- **Multi-industry runs:** the bundled script sums industry dimensions, which is right for
  quantities in numeraire units; check before quoting sector detail.
