# OG analysis studio

The standard deliverable (`og-scenario-report`) answers "what happened, in the house format."
This skill answers everything else — designed scenarios, ad-hoc questions, bespoke figures,
audience-shaped prose — with two absolutes:

1. **Everything generated is generated by code.** Every number in a chart, table, or paragraph is
   computed by a script from the run's actual outputs — never typed from memory, never estimated
   from another chart. Keep the script: each analysis gets a small directory (`analysis script +
   generated artifacts + a two-line README`) next to the run it analyzes, so any figure can be
   regenerated and audited later.
2. **Analysis never launches computation.** Designing, exploring, plotting, and writing are free.
   The moment a question needs a *new* solve (a redesigned reform, a missing baseline, a
   sensitivity sweep), stop: spec the run, estimate its duration, and ask — the family approval
   gates (the approval gates in SKILLS.md) bind here. Same for pushing or PR-ing any product of this skill.

## Mode 1 — Scenario design

Translate a policy question into a runnable reform spec *before* anyone runs anything:

- Output: a written spec — the exact `updated_params_ref` dict, phase-in path (year-by-year
  arrays where phased), the fiscal closure choice (`tG1`/`tG2`, which closure rule) and why, the
  expected transmission mechanisms (which margins should move, in which direction), and the
  estimated runtime.
- Check representability early: OG-Core has one economy-wide wage and no household sector choice;
  formal/informal wage gaps, sector-switching, and trade policy are *not* representable without
  extending the model — say so up front rather than bending a parameter to fake it. Industry-
  varying `cit_rate`/`tau_c` are fine; by-j tax parameters are not (t, s only).
- Check fiscal coherence at design time: a reform that changes revenue must say what absorbs it
  (closure rule vs offsetting instrument), or the transition will report the closure's behavior,
  not the policy's (see og-country-calibration → Fiscal consistency).
- Reform paths are inputs — plot them (mode 3) as part of the spec, so a mis-built phase-in is
  caught before it costs a solve.

## Mode 2 — Analytical exploration

Interrogate existing runs, inputs and outputs, in the repo's own venv:

- Load with `ogcore.utils.safe_read_pickle` on `SS_vars.pkl` / `TPI_vars.pkl` /
  `model_params.pkl`. Only ever load pickles from runs you or the user produced — a pickle is
  executable, so an OUTPUT dir of unknown origin gets the same suspicion as unknown code.
- Derive freely: ratios to Y, per-capita and per-cohort cuts, by-ability (j) incidence, growth
  contributions, differences-of-differences across runs, welfare-relevant aggregates. Compare as
  many runs as the question needs — nothing limits you to one baseline/one reform.
- Honesty rules travel with the numbers: model levels are not currency (`factor` converts,
  ratios don't need it); multi-industry consumption uses `p_tilde·C`; nominal sector shares are
  numeraire-distorted; "net exports" is a residual. State the caveat where the number appears.
- If a result looks wrong, don't explain it away — check the run first (`og-solver-diagnosis`,
  and the contamination heuristic in `og-run-preflight`).

## Mode 3 — Visualization

Bespoke figures, deliberately unbound from `plot_all`'s look:

- **Pick the best tool for the artifact, not the incumbent.** The country venvs guarantee
  matplotlib + pandas + scipy — that covers publication-quality statics (use a clean explicit
  style, not defaults). When the deliverable wants interactivity or linked views (plotly, altair)
  or heavier data handling (polars), create a *scratch analysis env* (`uv venv` + install what
  you need) and feed it data **exported from the repo venv as CSV/parquet** — don't install
  analysis libraries into a model repo's venv, and don't unpickle model objects outside it.
- If a project-level `dataviz` skill is installed, apply its palette/accessibility rules; they
  govern style, not chart choice.
- Charts of *inputs* (parameter paths, e-matrix slices, chi_n) are first-class citizens — they're
  the diagnostic the stock tooling lacks.
- Every figure ships with the script that made it and a caption stating run dirs and units.

## Mode 4 — Analytical write-ups

Prose shaped to the audience (ministry memo, technical annex, slide narrative, referee response):

- Structure is free — no template. What is not free: every quantitative claim traces to a
  computed value (keep the computation in the analysis script; consider printing a small
  "numbers used" appendix table from it), mechanisms are stated as mechanisms (which FOC, which
  constraint, which closure), and verified facts are separated from interpretation.
- State the run provenance once (repo, branch/HEAD if known, run dirs, calibration file) — a
  write-up that outlives the session must identify its runs.
- Drafts are drafts: show the user before anything is sent, published, or committed anywhere
  outside the analysis directory.
